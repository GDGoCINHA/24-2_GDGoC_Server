# Flyway 마이그레이션을 건드릴 때

- 파일명은 `V{YYYYMMDD}__{설명}.sql` 이다. **같은 날 두 개 이상을 만들 때는 `V{YYYYMMDD}_{순번}__{설명}.sql`** 을 쓴다 (`V20260806_1__…`, `V20260806_2__…`).
- **기존 파일을 수정하지 않는다.** 체크섬 불일치로 부팅이 실패한다.
- 이미 `origin/develop`·`origin/main`에 있는 마이그레이션은 `migration-guard.mjs` 훅이 편집을 차단한다. 내 브랜치에서 방금 만든 파일은 아직 적용된 적이 없으므로 통과한다.
- 스키마 변경은 반드시 마이그레이션으로 한다. `ddl-auto`에 의존하지 않는다.

## 같은 날짜는 충돌한다

Flyway는 파일명 전체가 아니라 **`V`와 `__` 사이만 버전으로 읽는다.** 설명이 달라도 날짜가 같으면 같은 버전이고, 부팅 시 이렇게 죽는다.

```
V20260806__create_notice_board.sql  →  version=20260806
V20260806__create_free_board.sql    →  version=20260806

FlywayException: Found more than one migration with version 20260806
```

버전 안의 `_`는 `.`으로 변환되므로 `V20260806_1__` 은 `20260806.1` 이 되어 충돌하지 않는다. 순번 없는 기존 파일(`V20260519__`)과도 순서가 어긋나지 않는다.

날짜를 하루 미뤄 회피하지 않는다 — 파일명이 실제 작업일과 어긋나 이력을 읽기 어려워진다.

## 되돌릴 수 없다

down 스크립트가 없어 **코드를 롤백해도 스키마는 남는다.** 롤백은 이전 커밋을 다시 push하는 것이 사실상 유일한 수단인데, 그것으로도 스키마는 돌아오지 않는다.

그래서 마이그레이션은 **배포 전에 되돌릴 수 없다는 전제로** 검토해야 한다. 컬럼 삭제나 타입 변경처럼 데이터를 잃는 변경은 특히 그렇다.

## 배포 순서

`develop`·`main` push가 곧 배포이며, 컨테이너 기동 시 Flyway가 자동 실행된다. 프론트엔드가 참조하는 필드를 바꿀 때는 **Server를 먼저 배포하고 Web을 나중에** 올린다.
